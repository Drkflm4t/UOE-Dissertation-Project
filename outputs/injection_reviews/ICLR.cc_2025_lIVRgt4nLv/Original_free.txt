Summary

This paper presents Agent S, an open framework for autonomous GUI-based computer control. The core proposal combines three ideas: (1) experience-augmented hierarchical planning, where a manager decomposes tasks into subtasks using retrieved web knowledge and narrative memory, and workers execute subtasks using episodic memory; (2) continual memory construction and update via self-supervised exploration and self-evaluation; and (3) an Agent-Computer Interface (ACI) that uses screenshots plus an OCR-augmented accessibility tree for perception and grounding, together with a bounded action space of high-level GUI primitives. On OSWorld, the paper reports 20.58% success with GPT-4o versus an 11.21% baseline, and also shows gains on WindowsAgentArena without explicit adaptation.

Overall assessment

This is a timely and interesting systems paper on multimodal GUI agents. The problem is important, the framing is clear, and the paper is well organized. The proposed architecture is sensible and practically motivated. I especially appreciate that the work is open-source, that it targets real desktop environments rather than toy settings, and that it includes ablations and error analysis rather than only headline numbers.

The strongest aspect of the paper is that it treats GUI control as a full agent systems problem rather than only a perception or action-generation problem. The combination of hierarchical planning, retrieval from multiple memory levels, and an explicit interface abstraction is coherent and well aligned with the challenges the authors identify in the introduction. The empirical gains on OSWorld are meaningful, and the cross-OS evaluation on WindowsAgentArena is a useful demonstration of portability.

That said, the paper also has important limitations. The absolute success rates remain low, making it difficult to judge practical readiness. Several methodological details are underspecified, especially around memory construction, retrieval, prompting, and evaluation protocol. Some comparisons are not fully controlled, and the contribution boundaries between “better prompting/interface design” and “learning from experience” are not always cleanly isolated. The self-supervised memory update mechanism is intriguing, but the evidence that it truly yields robust continual improvement rather than benchmark-specific accumulation is still limited.

Recommendation

Weak Accept

Reasons for this recommendation:
- Clear practical contribution with a coherent architecture.
- Strong improvement over the stated OSWorld baseline.
- Good ablation coverage and useful qualitative/error analyses.
- Open framework likely to be valuable to the community.

Main reservations:
- Limited methodological precision in several key components.
- Absolute performance is still modest.
- Some evaluation choices and claims need tighter justification.
- Novelty is more in integration and engineering than in fundamentally new learning algorithms.

Strengths

1. Important problem and strong motivation
The paper addresses autonomous desktop GUI control, which is both practically relevant and scientifically challenging. The introduction clearly identifies three central difficulties: domain knowledge, long-horizon planning, and dynamic interfaces.

2. Coherent architecture
The overall design in Figure 3 on page 4 is one of the paper’s strengths. The separation into Manager, Worker, Self-Evaluator, and ACI is intuitive. The distinction between narrative memory for high-level task summaries and episodic memory for subtask-level execution is also well motivated.

3. Useful ACI formulation
The ACI is a meaningful contribution. The dual-input design—screenshot for visual reasoning plus OCR-augmented accessibility tree for grounding—is practical and likely broadly useful. The bounded action space in Table 5 on page 15 is also a good design choice for safety and temporal feedback.

4. Strong empirical improvement over baseline
On OSWorld, the jump from 11.21% to 20.58% overall success with GPT-4o is substantial. The gains in Daily and Professional tasks are especially notable, as shown in Table 1 on page 8 and the bar chart on page 2. The WindowsAgentArena result in Table 4 on page 10 also supports some degree of generalization.

5. Ablations and analysis
The paper includes several ablations: removing web knowledge, narrative memory, episodic memory, ACI, exploration, continual update, and self-evaluator. This is better than many agent papers. The error taxonomy and statistics in Table 3 on page 10 are also helpful.

6. Qualitative examples
The examples in Figures 8–12 and failure cases in Figures 14–16 are useful. They make the system behavior concrete and reveal both strengths and brittleness.

Weaknesses and concerns

1. Novelty is somewhat incremental
The paper’s main novelty lies in integrating known ingredients: hierarchical planning, retrieval augmentation, memory, reflection, accessibility-tree grounding, OCR augmentation, and bounded action spaces. The integration is valuable, but the paper sometimes presents these as more conceptually novel than they are. The strongest claim should be around system design and empirical validation rather than algorithmic novelty.

2. Methodological details are insufficiently specified
Several important implementation details are missing or too vague for a top-tier conference standard:
- What exactly are the prompts for manager, worker, self-evaluator, and trajectory reflector?
- How many retrieved items are used from web, narrative memory, and episodic memory?
- How are memories stored, deduplicated, filtered, or truncated over time?
- What embedding similarity threshold or top-k retrieval is used?
- How is “similar task” defined in practice?
- How often does replanning occur, and under what exact conditions besides FAIL?
- What are the step limits per task and per subtask?
- How is OCR text merged into the accessibility tree when overlaps are partial or noisy?

Without these details, reproducibility is weaker than it should be, despite the code release.

3. Evaluation protocol raises some questions
The paper compares against OSWorld-reported baselines, but it is not always fully clear whether all settings are matched beyond input modality. For example:
- Are the same step budgets used?
- Are the same model versions and API dates used?
- Are prompt budgets and context lengths comparable?
- Is web search allowed for Agent S but not for the baseline? If so, this is a fair systems comparison only if clearly framed as such, but not a pure architecture comparison.

Similarly, on WindowsAgentArena, the comparison is to a “similar configuration” rather than the strongest system. That is understandable, but the claim should be phrased carefully.

4. Continual learning claims are stronger than the evidence
The paper emphasizes continual memory update and learning during inference. However, the evidence is limited. Figure 7 on page 9 shows some benefit from continual memory update, but this is still within the benchmark setting. It remains unclear:
- Whether performance improves monotonically over time.
- Whether memory accumulation causes interference or retrieval drift.
- Whether gains come from repeated exposure to similar benchmark templates.
- How robust the system is to stale or misleading memories.

A stronger continual-learning evaluation would track performance as a function of number of prior tasks, ideally on disjoint task families.

5. Self-evaluation may be noisy and self-reinforcing
The self-evaluator stores summaries of successful or failed trajectories without external supervision. This is interesting, but risky. If the evaluator misjudges a trajectory or summarizes a flawed strategy, the memory may reinforce errors. The paper acknowledges some execution and planning failures, but does not deeply analyze memory corruption or retrieval of bad experiences. Since both successful and failed trajectories are stored in narrative memory, more detail is needed on how failures are represented and prevented from harming future planning.

6. Absolute performance remains low
Although the relative improvement is large, 20.58% overall success on OSWorld is still low. This does not invalidate the contribution, but it should temper claims such as “uses computers like a human.” The title and framing are somewhat overstated relative to the actual capability level.

7. Some category-level results are uneven
The detailed app-level results in Table 8 on page 16 show regressions or weak performance in some domains, e.g., Calc is lower than baseline, and some WindowsAgentArena domains in Table 9 remain at 0%. This suggests the method may be particularly effective in some interface/task types but not others. The paper could do more to explain these patterns.

8. Writing and presentation issues
The paper is generally readable, but there are several issues:
- Some notation is inconsistent or overloaded.
- There are minor grammatical errors and awkward phrasing throughout.
- The references contain a duplicate entry for AutoGuide (2024a/2024b appear identical).
- The citation “OSWorld (OpenAI, 2023)” on page 2 appears incorrect.
- Some claims about “state-of-the-art” should be carefully contextualized given rapidly moving baselines and differing settings.

Detailed comments

1. On the ACI contribution
I found the ACI section compelling. The argument on pages 6–7 that MLLMs operate at slow, discrete intervals and therefore need temporally meaningful action primitives is well made. The OCR augmentation of the accessibility tree is also practical. However, I would like more quantitative evidence isolating which part matters most:
- accessibility tree IDs,
- OCR augmentation,
- bounded primitive actions,
- one-action-per-step feedback.

The current ACI ablation in Figure 6 is useful but still bundles multiple design choices.

2. On hierarchical planning
The manager-worker decomposition is sensible, but the paper does not fully show that the generated subtasks are consistently high quality. Since planning errors remain common, it would help to report:
- average number of subtasks per task,
- subtask completion rate,
- frequency of replanning,
- success conditioned on plan length.

The subtask failure rate in Table 3 is a good start, but more direct planning diagnostics would strengthen the claim.

3. On memory design
The distinction between narrative and episodic memory is intuitive. Still, the paper should clarify:
- whether narrative memory stores both successes and failures, while episodic stores only successful/DONE subtasks;
- whether failed narrative memories are retrieved equally often as successful ones;
- how the fusion prompt uses failure summaries constructively;
- whether memory size grows unboundedly.

This is central to the method and currently underexplained.

4. On self-supervised exploration
The memory bootstrap process in Figure 4 on page 6 is interesting, but also potentially benchmark-sensitive. The paper says it generates top 50 common tasks from applications used in OSWorld and WindowsAgentArena, and also environment-aware tasks based on benchmark initial states. This may be reasonable, but it risks partial adaptation to the benchmark distribution. I do not think this invalidates the results, but the paper should discuss it more explicitly. In particular, how different are the exploration tasks from the evaluation tasks? Is there any leakage in style, app state, or task templates?

5. On qualitative failures
The failure examples are informative. Figure 14 shows a nice case where planning, grounding, and execution errors interact. Figure 16 is especially revealing: the agent repeatedly clicks “Activity” instead of the intended GIMP tool. This suggests that despite the ACI, grounding remains a major bottleneck. It would be useful to know whether this is due to accessibility-tree ambiguity, OCR noise, prompt confusion, or action primitive limitations.

Questions for the authors

1. What exact prompts are used for the Manager, Worker, Self-Evaluator, and Trajectory Reflector? If space is limited, please include them in the appendix or repository.

2. How many items are retrieved from each source (web, narrative memory, episodic memory), and how are they ranked and truncated?

3. How large are the initial narrative and episodic memories after self-supervised exploration? How much do they grow during evaluation?

4. Are evaluation tasks processed sequentially such that later tasks can benefit from memories built on earlier test tasks? If so, please clarify the protocol carefully, since this affects interpretation.

5. How do you prevent contamination between exploration tasks and benchmark test tasks, especially for environment-aware task generation?

6. What is the computational cost of Agent S relative to the baseline, including number of model calls, wall-clock time, and web-search overhead?

7. In Table 8, why does Agent S underperform the baseline on Calc while doing much better on Writer, Thunderbird, VS Code, and GIMP? What failure mode is specific to spreadsheet tasks?

8. How often does the self-evaluator incorrectly label a trajectory as useful? Have you manually audited memory quality?

9. Does the system degrade when memories become large or contain contradictory experiences?

10. Can the method work without proprietary models such as GPT-4o/Claude-3.5, or is performance currently too low with open models?

Suggestions for improvement

1. Strengthen reproducibility
Include full prompts, retrieval hyperparameters, memory sizes, step budgets, and replanning logic in the appendix.

2. Add efficiency metrics
As the conclusion notes, step count and wall-clock time matter. Even a simple table with average steps, average model calls, and average runtime per task would be valuable.

3. Evaluate continual learning more rigorously
Show performance over time on a stream of tasks, ideally with held-out task families and analysis of memory growth and forgetting.

4. Isolate ACI components more cleanly
A finer-grained ablation would help separate the effects of OCR augmentation, ID grounding, and bounded action primitives.

5. Analyze memory quality
Provide examples of retrieved narrative and episodic memories that help versus hurt. Quantify how often retrieved memories are relevant.

6. Temper claims
The title and some wording imply near-human computer use, but the current success rates do not support that level of capability. A more measured framing would improve credibility.

7. Improve comparison clarity
Be explicit about what resources Agent S uses that baselines do not, especially web search and memory accumulation during evaluation.

Minor comments

- Page 2: “OSWorld benchmark (OpenAI, 2023)” appears to cite the wrong source.
- Page 3: The related work section is broad but could better distinguish this paper from concurrent cognitive-architecture GUI agents.
- Page 5: The statement that the structured response “allows the agent to generate a templated chain-of-thought” should be phrased carefully; many venues discourage explicit reliance on hidden CoT details.
- Page 8: “stratified sampled” should be “stratified-sampled” or “sampled using stratification.”
- Page 11 onward: references contain duplicated AutoGuide entries.
- Tables 8 and 9 on page 16 are useful and perhaps deserve discussion in the main text, not only appendix.

Final verdict

This is a solid and useful systems paper with meaningful empirical gains on a challenging benchmark. Its main contribution is the integration of hierarchical planning, retrieval-based experience, continual memory updates, and a practical GUI-oriented interface abstraction. The work is not radically novel algorithmically, and some methodological and evaluation details need tightening, but the overall package is strong enough to merit acceptance in a conference that values practical agent systems and benchmark progress.

Confidence: 4/5
